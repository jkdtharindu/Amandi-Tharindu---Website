## Model Assignment Convention
- Every open backlog item and Next Action below carries a `Model:` tag — the Claude model recommended for that task's complexity/risk, so it can be confirmed with the user (human-in-the-loop, per `HITL.md`) before work starts.
- Guide: **Opus 5** for architecture-defining, security-sensitive, or safety-critical work (schema/design decisions, anything touching HITL enforcement); **Sonnet 5** for well-scoped feature/CRUD/config work with low ambiguity; **Haiku 4.5** for small, mechanical, single-purpose fixes.
- Documentation-only passes — running `UPDATE_ME.md` or `SESSION_END_PROMPT.md` — default to **Haiku 4.5**: mechanical synthesis of a conversation that already happened, not a design decision. Escalate to **Sonnet 5** only if the pass has to adjudicate a genuinely ambiguous or contested decision.
- Completed (`[x]`) items are left untagged.
- If a task is added to this file without a `Model:` tag, flag it and propose one before starting — do not assume a default.

## Security & Logic Audit Follow-ups (2026-09-12)

Filed from a full-codebase audit (not a diff review) covering auth/session/CSRF, the API route layer, the data/backup architecture, and admin-panel frontend logic. Every item below was independently verified by reading the actual code, not taken on a sub-agent's word. Ranked most severe first.

**Promoted to numbered Next Actions 28-39 (same day)** after a review found these findings had been filed here but never turned into actual tracked tasks. The detail stays here; each Next Action below just points back to it rather than duplicating it.

- **`src/server.js` (legacy Express prototype) still fully implements guest login-by-name — a live auth bypass and invitation-code leak, even though the real Next.js app deliberately removed this.** `src/guest-auth/loginGuestByName.js` logs an unauthenticated caller in as any guest whose exact name they know, and its "candidates" fallback returns a JSON list of `{id, name, code}` — every matching guest's plaintext invitation code — for a partial/substring name match. `app/api/guest/login/route.ts:42-43`'s own comment says this was removed on purpose ("anyone who knew a guest's name could sign in as them" — PRD §15, owner decision 2026-09-10). The legacy path is still runnable (`npm run start:legacy`) and still covered by a passing test (`tests/guest-login-name.test.mjs`). The same legacy server's `/api/admin/login` also has no rate limiting at all (`createAdminLoginLimiter()` in `src/rate-limiter.js` is exported but never called anywhere), and `src/admin-auth/verifyAdminCredentials.js` returns before running the password KDF on an unknown email — a timing side-channel that lets an attacker enumerate valid admin emails. Neither issue exists in the real app's equivalents (`src/admin/adminAuth.js` explicitly guards against both). Recommend deleting the vulnerable auth paths from `src/server.js`/`guestRepo.js`/`guest-auth` rather than patching a prototype nobody should run against real data. (Model: Opus 5 — security-sensitive)

- **Table Arrangement dashboard stat cards go stale the moment you use the page.** `components/admin/TableArrangement.tsx:62-76` receives `dashboardStats` as a one-time server-rendered prop; every seat/unseat/add-table/delete-table action calls `load()` (line 92), which refreshes the seating grid but never recomputes `dashboardStats`. An admin seating 20 guests in one session sees "Table Arranged: 0 / Balance to Arrange: 50" the entire time, correcting only on a hard reload. (Model: Sonnet 5)

- **`EventManager.tsx` writes duplicate `displayOrder` values to the database.** Line 76's `setForm({ ...EMPTY_FORM, displayOrder: String(events.length) })` runs before `await load()` refreshes `events`, so it always computes the *pre-add* count. Adding two events back-to-back in one sitting (without manually editing the order field) gives both the same `displayOrder` — confirmed against `celebrationEventsRepo.js`'s sort-by-`displayOrder`, so this is a real, reproducible data-quality bug, not cosmetic. (Model: Haiku 4.5)

- **Two logout buttons fail unsafely.** `components/admin/AdminNav.tsx:22-27`'s `handleLogout` has no try/catch and never checks `res.ok` — a network hiccup during the fetch leaves the button permanently stuck on "Signing out…", and a server error is treated identically to success (redirects as if logged out either way). `components/guest/LogoutButton.tsx:10-22` has the same missing-`res.ok`-check gap for guests, with failures going only to `console.error` — a guest on a shared device can walk away believing they've logged out when they haven't. (Model: Haiku 4.5)

- **Editing a guest's other details can silently overwrite a correct seat count with a stale one.** In `GuestManager.tsx`, the Seats field is disabled and shows a live `existingInvitees.length` while editing a party with named invitees, but `form.slotCount` is frozen at whatever it was when the edit form opened (lines 119-132) — removing an invitee updates the display but not `form.slotCount`. Saving any other field afterward (e.g. a WhatsApp number fix) submits the stale count. Confirmed the server side does not protect against this: `PATCH /api/admin/guests/[id]` (`app/api/admin/guests/[id]/route.ts:55`) writes whatever `slotCount` it's given straight through — only the dedicated invitee-*removal* endpoint (Next Action 22) recomputes it from the real invitee list. (Model: Sonnet 5)

- **`SESSION_SECRET`'s production guard has a narrow trigger, and the in-memory dev fallback store uses guessable sequential guest IDs.** `src/session.js:3-7` only throws when `NODE_ENV` is the exact string `'production'` — any other run mode (a preview deploy that doesn't set that exact value, `npm run start:legacy` invoked directly, a misconfigured host) with `SESSION_SECRET` unset silently makes `signSession`/`verifySession` no-ops, so the `guest_session` cookie becomes just the raw guest ID. `src/data/guestStore.js:2-16` (the fallback used whenever `DATABASE_URL` is unset) assigns guests literal `'guest-1'`, `'guest-2'` ids — in that combination, `Cookie: guest_session=guest-1` logs an attacker in as that guest with no code at all. Production's real Postgres schema correctly uses `uuid` (`migrations/001_create_guests.sql:7`), so this is specific to a DATABASE_URL-unset + non-strict-production deployment — exactly what a misconfigured preview environment looks like. (Model: Sonnet 5)

- **Six Table Arrangement admin routes leak raw Postgres error text to the client.** `app/api/admin/table-arrangement/route.ts`, `[tableId]/route.ts`, `[tableId]/seats/[seatId]/assign/route.ts`, `[tableId]/seats/[seatId]/unassign/route.ts`, and `probable-attendees/route.ts` all forward `(error as Error).message` verbatim on any exception other than a unique-violation, unlike every other admin route (events/guests/sections/theme), which returns a fixed client-safe message and logs server-side. Admin-only exposure, so low severity, but worth matching the rest of the codebase's pattern. (Model: Haiku 4.5)

- **Guest RSVP `participantNames` has no size limit.** `app/api/guest/rsvp/route.ts:100-104` passes the request body's `participantNames` straight into `upsertRsvpResponse` with no count/length cap, unlike the admin-side invitee-name validation (`validateInviteeNames`, capped at 99 entries) or the guest invitee-request path (200-char cap per name). Any valid invitation code (printed on the wedding card, not secret) can currently submit an arbitrarily large array/strings. (Model: Sonnet 5)

- **Admin and guest logout routes skip CSRF verification**, unlike every other state-changing route in the app. `app/api/admin/logout/route.ts` and `app/api/guest/logout/route.ts` have no `verifyCsrfToken()` call — a cross-site auto-submitting form can force a signed-in admin or guest to log out. Low impact (no data touched), flagged only for consistency with the app's own CSRF policy. (Model: Haiku 4.5)

- **`WhatsAppReminderModal.tsx` has no keyboard accessibility** — no `role="dialog"`, no Escape-to-close, and focus is never moved into the dialog on open, so a keyboard-only admin has no way to dismiss it except tabbing all the way to the Cancel button. (Model: Haiku 4.5)

- **No production fail-closed guard for `DATABASE_URL` across 10 of the 11 data stores.** `src/data/adminStore.js` and `src/session.js` both hard-crash at boot if misconfigured in production; the guest/RSVP/theme/sections/table-arrangement/messaging/invitees/celebration-events/probable-attendees repos all just silently branch on `Boolean(process.env.DATABASE_URL)` with no equivalent check. Not currently triggered — `DATABASE_URL` is confirmed set in Vercel Production, and the team's own post-deploy checklist already verifies this by hand — but there's no code-level tripwire if it were ever accidentally unset, which on Vercel's per-invocation serverless model would silently split/lose data rather than error loudly. (Model: Sonnet 5 — proposed, unconfirmed)

- **`message_logs.guest_id` has no `ON DELETE` clause**, unlike `rsvp_responses` (`ON DELETE CASCADE`) and `table_seats.guest_id` (`ON DELETE SET NULL`) — `migrations/005_create_messaging.sql:14`. Currently dormant: `adminRepo.js`'s guest removal only ever soft-deletes (flips `is_deleted`), never issues a real `DELETE FROM guests`, so the missing clause can't be hit today. Worth a one-line fix (`ON DELETE CASCADE`, matching the RSVP table) so a future hard-delete path doesn't discover this as a foreign-key-violation crash. (Model: Haiku 4.5)

- **Minor/cosmetic, low priority:** `RsvpChart.tsx:30,41-49` rounds each segment's bar width independently, so three roughly-equal segments (e.g. 1/1/1 of 3) can visually undershoot 100% by a percent or two — the numeric labels underneath are still correct, just the bar. `ThemeEditor.tsx:21`'s default `fontFamilyOptions` prop lists "EB Garamond", which doesn't exist in the server's allow-list (`basicThemeValidation.js`) or in `fontFaces.js`'s font set — currently dead code (the real page always passes the correct list explicitly) but a trap if the component is ever reused without that override. (Model: Haiku 4.5)

Not re-filed here because they're already tracked elsewhere in this file: the client-spoofable `X-Forwarded-For` rate-limit key (Next Action 8 already considered and deliberately dropped a "spoof-resistant client-IP resolver" as Tier-3 over-engineering — see the PR #7 note) and guest sessions never expiring server-side (Next Action 19c, already noted as "fine at Tier 1; note it if the threat model changes").
