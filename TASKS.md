## Security & Logic Audit Follow-ups (2026-09-12)

Filed from a full-codebase audit (not a diff review) covering auth/session/CSRF, the API route layer, the data/backup architecture, and admin-panel frontend logic. Every item below was independently verified by reading the actual code, not taken on a sub-agent's word. Ranked most severe first.

**Promoted to numbered Next Actions 28-39 (same day)** after a review found these findings had been filed here but never turned into actual tracked tasks. The detail stays here; each Next Action below just points back to it rather than duplicating it.

- **`src/server.js` (legacy Express prototype) still fully implements guest login-by-name — a live auth bypass and invitation-code leak, even though the real Next.js app deliberately removed this.** `src/guest-auth/loginGuestByName.js` logs an unauthenticated caller in as any guest whose exact name they know, and its "candidates" fallback returns a JSON list of `{id, name, code}` — every matching guest's plaintext invitation code — for a partial/substring name match. `app/api/guest/login/route.ts:42-43`'s own comment says this was removed on purpose ("anyone who knew a guest's name could sign in as them" — PRD §15, owner decision 2026-09-10). The legacy path is still runnable (`npm run start:legacy`) and still covered by a passing test (`tests/guest-login-name.test.mjs`). The same legacy server's `/api/admin/login` also has no rate limiting at all (`createAdminLoginLimiter()` in `src/rate-limiter.js` is exported but never called anywhere), and `src/admin-auth/verifyAdminCredentials.js` returns before running the password KDF on an unknown email — a timing side-channel that lets an attacker enumerate valid admin emails. Neither issue exists in the real app's equivalents (`src/admin/adminAuth.js` explicitly guards against both).
