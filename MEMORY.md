[2026-09-03] Decision: The Theme Editor's `font_family` field is constrained to a curated set of 4 options (Default, Cormorant Garamond, Playfair Display, EB Garamond), each loaded via `next/font/google`, rather than accepting free text.

[2026-09-06] Decision: Backups are a catalog-driven JSON row dump (`scripts/backup-db.js`), not `pg_dump`.
Reason: `pg_dump` is not installed on this dev machine (Postgres never was — see the 2026-08-30 entry), and a backup procedure that cannot actually be run is worse than none, because it reads as covered. The JSON dump uses the `pg` driver the app already depends on, so it runs anywhere `npm test` does. Tables are read from `information_schema` rather than a hardcoded list, so a future migration cannot silently leave its table unbacked — the same drift class that has already bitten this project twice.
Alternative considered: `pg_dump` — rejected as unrunnable here, and it would make the procedure depend on a binary nobody has verified. Relying solely on Neon's point-in-time restore — rejected as a single layer, since it does not survive account loss or a retention window that has already rolled past the mistake; it remains the preferred *first* resort and is documented as such in `docs/BACKUP_RECOVERY.md`.

[2026-09-06] Decision: the restore script (`scripts/restore-db.js`) takes its target from `RESTORE_TARGET_URL` and never falls back to `DATABASE_URL`, and it builds its own `pg.Pool` rather than importing `src/db.js`.
Reason: `src/db.js` binds a module-level pool to `DATABASE_URL`, so any restore code importing it would be one missing flag away from overwriting production. Making the target a separate, deliberately-stated variable means merely having `.env` loaded can never reach the live database — the dangerous operation requires an extra act of intent rather than the absence of one. A dry run is exempted from the same-database refusal because it provably cannot write (it returns before `BEGIN` and issues only `SELECT`s); requiring the overwrite flag for a read-only check would only teach the habit of typing it.
Alternative considered: reusing `src/db.js` and gating on a confirmation prompt — rejected because a prompt is a thing a tired person clicks through at 1am, whereas a target that simply is not configured cannot be clicked through. Also considered hardcoding the parent-first table order (as `docs/BACKUP_RECOVERY.md` previously described in prose) — rejected because it rots the moment a migration adds a foreign key; the order is derived from the target's own catalog instead, the same reasoning that makes the backup discover its tables rather than list them.

[2026-09-06] Decision: backups going off this laptop are encrypted first (`npm run backup:encrypt`, AES-256-GCM with a scrypt-derived key from `BACKUP_PASSPHRASE`), after which any private cloud folder is an acceptable home. Owner's call, chosen over a password manager, an offline external drive, or an unencrypted private cloud folder.
Reason: it decouples the storage decision from the PII risk. Every backup holds each guest's name, phone number and email, so unencrypted storage made the location choice load-bearing and every convenient option slightly wrong. Encrypting first makes the convenient option correct, which is the option that will actually get used week after week — a backup routine nobody follows protects nothing. Implemented with Node's own crypto rather than `age` or `gpg` on exactly the reasoning that ruled out `pg_dump` (2026-09-06 entry above): neither binary is installed here, and a backup that cannot be decrypted on the machine in front of you is worse than none.
Alternative considered: a password manager's secure file storage — fine for a 12 KB file and genuinely private, but manual every time, so it decays. An offline external drive — strongest against ransomware and account loss, weakest against human memory. Unencrypted private cloud — rejected as the thing `docs/BACKUP_RECOVERY.md` already warned against. Accepted trade-off, stated in the doc rather than buried: losing the passphrase loses the backup, so the passphrase must be stored somewhere retrievable that is not the backups folder.
