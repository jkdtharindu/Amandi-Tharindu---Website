[2026-09-05] Decision: ProbableAttendee (Table Arrangement Dashboard, P1-16) is an anonymous placeholder — never linked to a `guests` row, never changes `rsvp_status` — rather than a per-guest "probable" flag on Declined/Pending Guests.

[2026-09-12] Decision: Individual invitee RSVP & seating (multi-person invitations) is a new additive `invitees` table (migration 012) keyed off `guest_id`, not an extension of the existing `rsvp_responses.participant_names` free-text array — and party-level `rsvp_status` becomes 'accepted' the moment any one invitee accepts, 'declined' only once every invitee has declined.
Reason: the owner wanted per-person accept/decline for a multi-person invitation (admin names each person up front) plus a guest-initiated "add another person" request requiring admin approval — neither is expressible in a flat text array with no per-name status or identity. A real child table gives each person a stable id, which `table_seats` can then reference for individual seating (a third occupant type alongside `guest_id`/`probable_attendee_id`, exact same additive pattern migration 010 used for ProbableAttendee: `ADD COLUMN IF NOT EXISTS`, a rewritten `chk_seat_single_occupant` allowing at most one of the three, its own partial unique index). Existing single-person guests never get an `invitees` row, so their RSVP/seating behavior is completely untouched.
Alternative considered: keeping `participant_names` but adding a parallel status array — rejected as unable to carry identity (no id to seat individually) or an approval state (guest-requested additions) without becoming a second, shadow schema bolted onto a text column. Requiring the admin to enter an exact headcount number separately from the name list — rejected per owner's explicit answer: headcount is derived from however many names are typed, removing a place for the two to disagree. See TASKS.md's Phase 4 entry and `migrations/012_create_invitees.sql` for the full design.

[2026-09-12] Decision: `syncGuestSlotCountToInvitees` (built for Next Action 22, invitee removal) recomputes a guest's `slot_count` from the ground truth — a live `COUNT(*)` of that guest's remaining approved `invitees` — rather than decrementing the existing value by one.
Reason: the admin edit form already lets `slot_count` be typed directly regardless of whether the party has named invitees (the field is only made read-only when creating a party with invitee names, not when editing one that already has them — a pre-existing gap, now also closed at the UI layer in the same change), so a relative -1 could compound an existing, real drift rather than correct it. Recomputing from source is self-healing: whatever `slot_count` said before, it becomes accurate after. `incrementGuestSlotCount` (approving a guest-requested addition) was deliberately left as a blind +1, not changed to match — that call site has no equivalent drift risk, since approval is the only writer of that specific transition.
Alternative considered: mirroring `incrementGuestSlotCount`'s blind `slot_count = slot_count - 1` — rejected because it does not correct drift and can be made to disagree with the real invitee count.

[2026-09-12] Decision: When a Phase 6 page gets folded into a homepage section, its old route redirects via `next.config.ts`'s `redirects()` (config-level), not a page component that calls `redirect()`.
Reason: the page component is deleted entirely (its content moved into `app/(public)/page.tsx`), so there's no page left to hold a `redirect()` call. `proxy.ts`'s site gate (middleware) runs before `next.config.ts` redirects in Next.js's request pipeline, so a signed-out visitor to the old path still gets gated exactly as before — the redirect only ever fires for a signed-in guest, which is the only audience that content ever had. Established with `/our-story` → `/#our-story`; the same pattern applies to `/the-celebration` and `/gallery` when those fold in.
Alternative considered: keeping a thin page component at the old route that just calls Next's `redirect()` — rejected as unnecessary indirection once `next.config.ts` handles it declaratively with no server component needed.

[2026-09-15] Decision (Action 37, Grill Me session): outbound guest messages (the single-guest WhatsApp reminder, and every Messaging Center template) never put the invitation code inside a clickable link. The `/invitation/[code]` route itself is unchanged — it stays exactly as it was, still used by the nav's "Invitation" link once a guest is signed in.
Reason: investigating the three originally-filed candidate fixes surfaced that the real mechanism was different from how the item was scoped. The invitation code is the site's *only* login credential (no separate password exists), and a signed-in guest already could not view anyone else's `/invitation/[code]` — `app/(public)/invitation/[code]/page.tsx` redirects them to their own code if the URL doesn't match their session. So the actual leak was never the route being reachable; it was that `buildInvitationLink()` baked the code into the one link a guest receives (via WhatsApp), so forwarding that message handed a third party a single-tap login with nothing to type. This also means the originally-filed candidate (b) — "make `/invitation/[code]` redirect to login if not authenticated, then back" — would not have changed anything: a signed-out visitor was already redirected to the gate by `proxy.ts`, and the gate needs that exact same code to open, so "logging in" and "reading the code already sitting in the URL" are the same action. Put to the owner directly once this was understood, alongside candidates (a) full route removal and (c) expiring/one-time tokens; the owner chose to keep the route and only change what the link contains, as the smallest fix that actually addresses the real mechanism, without new schema or breaking the nav/bookmarks path — consistent with this project's Tier-1 sizing (`docs/VIBE_CODING_PRODUCTION_CHECKLIST.md`).
Alternative considered: removing the `/invitation/[code]` route entirely (option a) — rejected as more invasive than needed once the actual leak was understood to be link-construction, not route-existence; would also have broken the nav's "Invitation" link and needed a new session-only equivalent. Expiring/one-time tokens (option c) — rejected as real new engineering (a schema change, expiry logic, and a UX decision for a guest whose own link goes stale) to protect against a threat this project's own Tier-1 calibration doesn't treat as needing that weight, for a few-hundred-guest personal site where RSVP status is not highly sensitive data.

[2026-09-16] Decision (Action 28): the legacy Express prototype's guest login-by-name was **deleted**, while its two admin-login weaknesses were **fixed in place** — a deliberate split, not an inconsistency.
Reason: the audit's standing advice was "delete the vulnerable code rather than patch a prototype nobody should run against real data," and for login-by-name that was straightforward — the real Next.js app had already removed it on purpose (PRD §15), so deleting `loginGuestByName.js`, its two `guestRepo` helpers and the legacy login page's candidate-list UI left the two servers *agreeing* rather than diverging further. The admin login could not take the same treatment: eight test files drive `/api/admin/login` against `createApp()`, so deleting the route would delete a large part of this project's actual test coverage. Pointing it at the hardened `src/admin/adminAuth.js` was also ruled out on inspection — that module reads `ADMIN_EMAIL`/`ADMIN_PASSWORD_HASH` from `process.env`, while the legacy server and every one of its test fixtures seed the `adminStore` array directly, so reusing it would have meant either weakening the real app's module to accept store records or breaking every admin test. So the timing side-channel was closed in `src/admin-auth/verifyAdminCredentials.js` itself (always run scrypt, against a dummy hash when no record matches — the same guard `src/admin/adminAuth.js` already documented), and the missing rate limit was closed by finally *calling* `createAdminLoginLimiter()`, which had existed and been unit-tested in `src/rate-limiter.js` since 2026-09-06 without a single caller.
Alternative considered: deleting `src/server.js` wholesale — the honest end state, and rejected only because it is blocked on porting its tests, which is a separate architecture decision rather than part of a security fix; filed as Next Action 47 instead of being quietly skipped. Also considered leaving (b) and (c) alone on the grounds that a prototype does not warrant hardening — rejected because the prototype is runnable (`npm run start:legacy`) against whatever `DATABASE_URL` is set, which on a developer's machine is production; "nobody should run it" is a convention, not a control.
Verification note worth reusing: the timing fix was only trusted after the new test was **watched failing** against the restored vulnerable version — unknown email 0.035ms vs known email 742ms, a ~21,000x gap. This file records three prior instances of a security control that was written, tested and committed without anything ever observing it fail; a timing assertion is especially prone to that, since one that is too loose passes no matter what the code does.

[2026-09-17] Decision (Next Action 40, migration 018): `message_logs.guest_id` gets `ON DELETE CASCADE`, and the migration finds the existing foreign key by querying `pg_catalog` (`pg_constraint`) rather than dropping it by an assumed name.
Reason: migration 005 declared the key as a bare `REFERENCES guests(id)`, unlike every other table that points at `guests` (`rsvp_responses` CASCADE, `table_seats.guest_id` SET NULL). Dormant today — guest removal only ever soft-deletes — but the first real hard delete (a "delete my data" request is the obvious one) would fail with a foreign-key violation for any guest who had ever been messaged. CASCADE rather than SET NULL because `guest_id` is NOT NULL and a message log with no guest has no value. The key was created unnamed, so its name is Postgres's default (normally `message_logs_guest_id_fkey`); `DROP CONSTRAINT IF EXISTS <assumed name>` would silently do nothing on a mismatch and leave the old non-cascading key beside the new one, still blocking deletes — so the migration looks up whichever foreign key actually links `message_logs.guest_id` to `guests` and drops that by its real name. The runner applies the file in one transaction, so there is no moment without a key; safe to re-run.
Alternative considered: `SET NULL` (rejected — the column is NOT NULL); dropping by the assumed default name (rejected for the silent-no-op reason above). **Status: written 2026-09-17, committed 2026-09-18 in `85c8acc`, NOT applied to the live database** — the owner must run `npm run migrate` from their own terminal (blocked for Claude even after HITL approval). Nothing in the unpushed code depends on the cascade, so pushing before the migration runs breaks nothing.

[2026-09-18] Decision (Next Action 33): guest and admin session cookies are **always signed**; the `useSignature` on/off mode in `src/session.js` was removed rather than tightened. Outside production, an unset `SESSION_SECRET` now gets a random per-process secret (with a warning) instead of switching signing off.
Reason: the old rule made signing a no-op whenever `SESSION_SECRET` was unset outside production, and the in-memory fixtures use predictable ids (`guest-1`, `guest-2`), so `Cookie: guest_session=guest-1` was a working login in any dev or preview environment missing the variable; the production guard also only fired on an exact `NODE_ENV=production` match. Production already refused to boot without a secret, so this changes nothing about the live site's requirements — it closes the non-production hole.
Alternative considered: randomising the fixture ids in `src/data/guestStore.js` — rejected, because once signing is unconditional the ids stop being guessable *credentials*, and randomising them would cost every test its `guest-1` handle for no security gain (the comment now atop `guestStore.js` records this). Trade-off accepted: dev sessions no longer survive a dev-server restart unless `SESSION_SECRET` is set (documented in `.env.example`).

[2026-09-20] Decision (Next Action 49): a guest's RSVP is saved in **one database transaction**, and a failed write now **surfaces to the guest as an error** instead of being logged and swallowed. Done by giving the repo functions an optional trailing `exec` (a transaction's query function) and composing them in a new `src/rsvp/saveRsvp.js`, not by writing a second copy of the SQL inside a transaction.
Reason: saving was two or three unrelated writes (`rsvp_responses`, `guests.rsvp_status`, and per-invitee answers). The route caught a failure of the last one, logged it and still returned success — so the guest was told "saved" while the admin dashboard, which reads `guests.rsvp_status`, kept showing "pending". Surfacing the failure trades a rare visible error (the guest retries) for certainty that a "saved" toast means both places agree. Passing `exec` keeps one copy of each statement; supplying it also selects the SQL branch in the repos, which is what lets tests drive the DB path with a fake. The guest row is also locked (`SELECT … FOR UPDATE`) at the start because `rsvp_responses.guest_id` has no unique constraint — two concurrent submissions (a double-tapped Submit) could each see "no row yet" and each insert one.
Alternative considered: keep swallowing and add a reconciliation/retry path (rejected — more machinery to hide a failure the guest can simply retry); write the SQL inline in a new transactional function (rejected — a second upsert to keep in sync with the first); `INSERT … ON CONFLICT` (rejected — needs a unique constraint, i.e. a migration plus deduplicating any existing rows). **Limits, stated plainly:** there is no Postgres in the test environment, so the tests use a fake transaction that records statements. They prove every statement runs through the one transaction, the guest is locked first, and a failure propagates to a rollback — not that the SQL (including the new `FOR UPDATE`) is valid against a real database. That is verified by the first real RSVP after deploy. In-memory mode (no `DATABASE_URL`) has no rollback and needs none.

[2026-09-20] Decision (Action 50 Grill Me): removing one person from a party is **one all-or-nothing transaction** — free the seat, delete the person, save the party's RSVP response and status, fix the headcount — and **the last approved person in a party cannot be removed** (the admin uses Remove on the guest's row instead). [2026-09-20] Decision (Table Arrangement review, Actions 59-60): assigning a person to a seat that already holds someone else is **refused** (HTTP 400, "That seat already has someone on it."); the seat has to be emptied first with Remove. 2) Technology choices and why alternatives were rejected

[2026-09-12] Decision: every store in `src/data/*.js` (`themeStore`, `guestStore`, `rsvpStore`, `adminStore`, `sectionsStore`, `tableArrangementStore`, `messageLogStore`, `messageTemplatesStore`, `probableAttendeesStore`, `celebrationEventsStore`, `inviteesStore`) backs its exported singleton with `globalThis` (e.g. `globalThis.__themeSettings ??= {...defaults}`) instead of a plain top-level `const`/object literal.
Reason: in the in-memory (no `DATABASE_URL`) dev/test mode, Turbopack's dev module graph was instantiating each store module *twice* — once per bundle family (confirmed: Route Handlers got one instance, Page Server Components got another) — so a write via one was invisible to a read via the other. Confirmed via `curl` (no browser cache involved): `PUT /api/admin/theme` (Route Handler) persisted a value that `GET /api/admin/theme` read back correctly, but `/admin/theme` and `/` (Page Server Components, one already forced fully dynamic via `cookies()`) kept rendering the old value — ruling out any Next.js page/ISR cache explanation (`export const dynamic = 'force-dynamic'` didn't fix it either, and a `force-dynamic` route is never cached, full stop). This was the root cause of two separately-filed, previously-mysterious bugs at once: the Next Action 27 theme-settings staleness and the Next Action 26 guest `/invitation` redirect — confirmed as the same fix for both, not a coincidence. `globalThis` is one process-wide object no matter how many separate module instances Turbopack creates, so it sidesteps the duplication entirely; this is the standard fix for this exact class of bug, the same pattern commonly used for Prisma Client singletons in Next.js apps. It does **not** reproduce on the real DB-backed path — confirmed by reading `src/db.js`: `query()` opens a real `pg` connection per call with no module-level cache, so every route hits the same real table regardless of which Turbopack bundle compiled it. This was specific to the in-memory testing convenience mode, not a production risk.
Reason this matters for future debugging: if a future session sees a write via one route not reflected by a read via another, in in-memory dev mode specifically, this class of bug should already be closed — but the diagnostic technique (curl-testing a Route Handler against a Page Server Component for the same data, bypassing all browser caching) is worth reusing for any *new* in-memory store added later that forgets this pattern.
Alternative considered: chasing it as a `revalidatePath`/ISR caching problem, since `revalidatePublicPages.js`'s own comment had already flagged Turbopack revalidation as unverified — this was a dead end (see the `force-dynamic` test above) and cost real investigation time before the actual mechanism (module duplication, not caching) was found via direct `curl` comparison of a Route Handler against a Page Server Component.
Verification: `tests/store-globalthis-sharing.test.mjs` forces two genuine separate module instantiations per store via cache-busting dynamic imports (`import(url)` then `import(url + '?instance=2')`), and asserts the exported binding is the same object both times — confirmed these tests actually fail without the fix by temporarily reverting one store and re-running. Also verified live end-to-end against an isolated in-memory server with a synthetic test-only admin login.

[2026-09-03] Decision: The Theme Editor's `font_family` field is constrained to a curated set of 4 options (Default, Cormorant Garamond, Playfair Display, EB Garamond), each loaded via `next/font/google`, rather than accepting free text.
Reason: this codebase had no font-loading infrastructure at all before this slice (no `next/font`, no Google Fonts `<link>`, no `@font-face`) — the PRD default font (`Cormorant Garamond`) is a Google Font, so an arbitrary admin-typed name would silently fail to render for visitors without it installed, making the feature look broken.
Alternative considered: free-text `font_family` matching the PRD's literal `text` column type — rejected because it doesn't work without matching font infrastructure that doesn't exist yet.

[2026-09-06] Decision: Backups are a catalog-driven JSON row dump (`scripts/backup-db.js`), not `pg_dump`.
Reason: `pg_dump` is not installed on this dev machine (Postgres never was — see the 2026-08-30 entry), and a backup procedure that cannot actually be run is worse than none, because it reads as covered. The JSON dump uses the `pg` driver the app already depends on, so it runs anywhere `npm test` does. Tables are read from `information_schema` rather than a hardcoded list, so a future migration cannot silently leave its table unbacked — the same drift class that has already bitten this project twice.
Alternative considered: `pg_dump` — rejected as unrunnable here, and it would make the procedure depend on a binary nobody has verified. Relying solely on Neon's point-in-time restore — rejected as a single layer, since it does not survive account loss or a retention window that has already rolled past the mistake; it remains the preferred *first* resort and is documented as such in `docs/BACKUP_RECOVERY.md`.

[2026-09-06] Decision: TASKS.md Next Action 8 (security & production readiness) is right-sized to **Tier 1 only**, per `docs/VIBE_CODING_PRODUCTION_CHECKLIST.md`'s own project-size table (a small/personal project — wedding site, one server, no payments — maps to Tier 1 only). Dropped: moving rate-limit counters to a shared store (**Tier 3** — the checklist's own worked example, written for this exact project, names this specific item as prior over-engineering) and giving CSRF tokens a TTL (Tier 1 is already satisfied by the existing double-submit-cookie protection; a TTL is a Tier 2+ refinement). Moved off the action entirely as not security items: `updated_at` on `guests` (a data-quality nicety needing its own HITL migration decision) and `NEXT_PUBLIC_SITE_URL` (a prod env var, relocated to Action 10/deployment). Kept as the one remaining Tier 1 item: a guest-data privacy review (no PII in logs; confirm soft-delete satisfies "delete on request").
Reason: the owner asked whether the remaining Action 8 follow-ups were actually required for a site this size, rather than assuming the checklist's full list applied by default. Re-reading the checklist itself (not just Action 8's prose) showed it explicitly warns against this: applying commercial-production-app checklist items to a small project "is itself a mistake" that "spends real time on defences that protect nothing."
Alternative considered: finishing all five of Action 8's original sub-items as scoped on 2026-09-06 — rejected because the checklist, once actually read in full, does not call for that at this project's declared size; doing so anyway would repeat the exact over-engineering pattern the checklist's own worked example (for this project) describes.

[2026-09-06] Decision: the restore script (`scripts/restore-db.js`) takes its target from `RESTORE_TARGET_URL` and never falls back to `DATABASE_URL`, and it builds its own `pg.Pool` rather than importing `src/db.js`.
Reason: `src/db.js` binds a module-level pool to `DATABASE_URL`, so any restore code importing it would be one missing flag away from overwriting production. Making the target a separate, deliberately-stated variable means merely having `.env` loaded can never reach the live database — the dangerous operation requires an extra act of intent rather than the absence of one. A dry run is exempted from the same-database refusal because it provably cannot write (it returns before `BEGIN` and issues only `SELECT`s); requiring the overwrite flag for a read-only check would only teach the habit of typing it.
Alternative considered: reusing `src/db.js` and gating on a confirmation prompt — rejected because a prompt is a thing a tired person clicks through at 1am, whereas a target that simply is not configured cannot be clicked through. Also considered hardcoding the parent-first table order (as `docs/BACKUP_RECOVERY.md` previously described in prose) — rejected because it rots the moment a migration adds a foreign key; the order is derived from the target's own catalog instead, the same reasoning that makes the backup discover its tables rather than list them.

[2026-09-06] Decision: backups going off this laptop are encrypted first (`npm run backup:encrypt`, AES-256-GCM with a scrypt-derived key from `BACKUP_PASSPHRASE`), after which any private cloud folder is an acceptable home. Owner's call, chosen over a password manager, an offline external drive, or an unencrypted private cloud folder.
Reason: it decouples the storage decision from the PII risk. Every backup holds each guest's name, phone number and email, so unencrypted storage made the location choice load-bearing and every convenient option slightly wrong. Encrypting first makes the convenient option correct, which is the option that will actually get used week after week — a backup routine nobody follows protects nothing. Implemented with Node's own crypto rather than `age` or `gpg` on exactly the reasoning that ruled out `pg_dump` (2026-09-06 entry above): neither binary is installed here, and a backup that cannot be decrypted on the machine in front of you is worse than none.
Alternative considered: a password manager's secure file storage — fine for a 12 KB file and genuinely private, but manual every time, so it decays. An offline external drive — strongest against ransomware and account loss, weakest against human memory. Unencrypted private cloud — rejected as the thing `docs/BACKUP_RECOVERY.md` already warned against. Accepted trade-off, stated in the doc rather than buried: losing the passphrase loses the backup, so the passphrase must be stored somewhere retrievable that is not the backups folder.

[2026-09-13] Decision: when rotating a live secret (Action 18a, the Neon `DATABASE_URL` password), the new credential's value is never typed into the chat by the owner and never printed by any tool output the session can see — a small Node script reads the owner-downloaded credential file and the existing `.env` directly, splices the new value into the existing `DATABASE_URL` (keeping the untouched host/database/params), writes it back to `.env`, and prints only redacted confirmation (username, character count) — the password itself never appears in any command's visible output. Verification that the new credential actually works used `npm test` (458/458 passing) rather than a direct `SELECT` against production, since this environment's own safety classifier blocks direct production-database queries outright.
Reason: the entire reason Action 18a exists is that the *previous* password ended up exposed by being pasted into a chat transcript — reusing that same pattern to install its replacement (asking the owner to paste the new one so it could be copied into files) would repeat the exact mistake being fixed. Verifying via the existing test suite is also strictly safer than a scratch verification query: it exercises the real connection path the app itself uses, produces no new one-off script to forget about, and needs no special-case permission.
